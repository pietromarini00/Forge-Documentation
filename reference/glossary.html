Glossary

Domain terms and platform-specific concepts used throughout the codebase.

Domain Terms

CDE (Common Data Element) A standardized variable definition used across studies or organizations. Defines a field’s name, type, allowed values, and constraints. Example: age_at_onset (integer, 0-120, required). CDEs are the atomic unit of a schema.

Schema A named, versioned collection of CDEs that defines what a dataset should look like. Example: “GP2 Clinical Data Elements v3” contains 47 CDEs. Stored in the Registry Service.

Data Dictionary A spreadsheet or file listing the fields in a source dataset, typically with columns like variable name, type, description, and allowed values. This is the input to harmonization — the thing being mapped from.

Harmonization The process of mapping fields in a source data dictionary to CDEs in a canonical schema. Example: mapping pt_age in a site’s data to age_at_onset in the canonical schema.

Curation The process of reviewing and cleaning a raw CDE list into a publishable schema. Includes renaming, typing, deduplication, constraint definition, and validation rule authoring.

Gold Dataset A named, schema-bound collection of accepted submission data. Contains only reviewed and approved records with full provenance. Example: “GP2 Pilot Cohort” — 3,200 records from 12 accepted submissions.

Provenance The lineage trail attached to every row in a gold dataset: which submission it came from, which version, which source row, when it was accepted, and by whom. Stored as extra columns: _submission_id, _version, _source_row, _accepted_at, _accepted_by.

Value Set A controlled list of allowed codes and display labels. Can be flat (simple list) or hierarchical (parent-child). Example: a “Sex” value set with codes M, F, U and display labels “Male”, “Female”, “Unknown”. Stored in the Registry Service and referenced by schema elements.

Identifier Scheme Configuration on a gold dataset that defines how records are identified and deduplicated. Specifies source IDs (from submitters), golden IDs (generated by the platform), generation strategies (UUID, template, composite), and what to do on duplicate (reject, flag, update).

Platform Terms

SchemaForge The schema lifecycle layer of Forge. Covers: creating schemas (curation), mapping to schemas (harmonization), and storing schemas (registry). Implemented across Registry Service + forge-app curation/harmonization modules.

DataForge The data lifecycle layer of Forge. Covers: uploading data, validating against schemas, QC review, corrections, and gold dataset management. Implemented as a standalone FastAPI service.

Registry Service FastAPI + PostgreSQL service that stores schemas, elements, value sets, and version history. The single source of truth for “what should data look like.” Port 8000.

forge-app The unified Streamlit web application that provides the UI for all workflows (schema curation, harmonization, data validation, gold datasets). Port 8505. This is the primary user-facing application.

Manifest A JSON file that tracks the state of a user’s project. Two types: SchemaProjectManifest (tracks curation wizard progress) and DataProjectManifest (tracks the harmonization + validation pipeline). Persisted in .cache/forge-app/.

Submission A data file uploaded to DataForge for validation. Has a lifecycle: UPLOADED → VALIDATING → PENDING_REVIEW → ACCEPTED/REJECTED. Can have multiple versions (corrections). Each version has its own validation result.

Validation Result The output of running a data file against a schema. Contains a list of issues (errors, warnings) with row numbers, field names, and messages. A submission is valid if it has zero ERROR-severity issues.

Validation Rule A cross-field constraint beyond basic type/value checking. Two kinds: CONDITIONAL (if field A has value X, then field B must satisfy Y) and SUBMISSION (applies across all rows, like uniqueness). Stored in the Registry schema’s metadata.validation_rules JSONB field.

Audit Log An append-only JSONL file that records every action taken on a submission (created, validated, claimed, accepted, rejected, etc.). One file per submission. Never modified or deleted.

Technical Terms

Hybrid Retrieval The candidate selection method used in harmonization. Combines TF-IDF (lexical/keyword matching) and sentence-transformer embeddings (semantic matching) to find the top-K most similar CDEs for a given source field. Implemented in forge-retrieval-core.

Two-Tier Matching The harmonization matching strategy. Tier 1: exact name match against CDE items and alternate names (deterministic, instant). Tier 2: hybrid retrieval → top 15 candidates → Claude API evaluates and scores (AI-powered, slower). If Tier 1 matches, Tier 2 is skipped.

ComprehensiveMatcher The class that implements two-tier matching. Lives in forge-app/core/harmonization/matcher.py. Takes a reference schema and a source data dictionary, returns match results with confidence scores and rationale.

HybridRetriever The class that implements hybrid retrieval (TF-IDF + embeddings). Lives in forge-app/core/harmonization/retrieval.py. Uses forge-retrieval-core library. Caches embedding indices to disk per project.

AISuggestionService The class that generates AI-powered suggestions during schema curation. Sends batches of raw elements to Claude, gets back suggested names, types, descriptions, constraints, and allowed values. Lives in forge-app/core/curation/suggestion_service.py.

DuplicateDetector Uses TF-IDF + embedding similarity (via forge-retrieval-core) to find near-duplicate variables in a CDE list. Groups them for merge review during curation. Lives in forge-app/core/curation/duplicate_detector.py.

StorageBackend A Python Protocol in DataForge that abstracts how submissions and files are persisted. Currently implemented as LocalFileBackend (filesystem). Designed to be swappable to S3, GCS, or database storage.

RegistrySchemaLoader A class in DataForge that fetches a schema from the Registry Service API at validation time. Converts the Registry’s element format into DataForge’s internal Schema / FieldConfig models. This is how DataForge knows what rules to enforce.
