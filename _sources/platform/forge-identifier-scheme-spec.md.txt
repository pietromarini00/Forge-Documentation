# Identifier Schemes & Golden IDs — Spec

## Overview

Add a configurable identifier management system to Gold Datasets in DataForge. Data managers define an **Identifier Scheme** on each gold dataset that specifies: which columns are source IDs (provided by submitters), which are golden IDs (generated by the platform), how golden IDs are generated, and how incoming records are deduplicated against existing data.

This replaces the current single `key_column` field on `GoldDataset` with a general-purpose system that handles hierarchical IDs, cross-system mappings, and project-specific naming conventions.

---

## Problem Statement

Research consortia and data integration projects routinely deal with multiple identifier systems:

- **GP2:** Sites submit samples with internal IDs. The platform assigns a `gp2id` (unique person) and `gp2sampleid` (`{gp2id}_s{N}` for repeat genotyping).
- **PathND:** Sites submit samples. The platform assigns a `pathnd_id` (unique person) and an `image_id` per image for that person.
- **HRIS migrations:** Users have an ID in one system, a different ID in the new system, plus auxiliary identifiers (SSN, DL number).

Common patterns across these:

1. **Source IDs** come from submitters and must be preserved
2. **Golden IDs** are assigned by the platform and follow a naming convention
3. Golden IDs can be **hierarchical** — a child ID is derived from a parent ID
4. **Deduplication** uses source IDs (or combinations of fields) to detect records already in the gold dataset
5. **ID generation** varies by project: sequential with prefix, UUID, composite from other columns

The current `key_column: str | None` on `GoldDataset` only supports single-column exact-match dedup. There is no concept of source vs golden IDs, no ID generation, and no hierarchy.

## Design

### Core Data Model

#### IdentifierDef

Defines a single identifier column in the gold dataset.

```python
class IdClass(str, Enum):
    SOURCE = "source"    # Provided by submitter, preserved as-is
    GOLDEN = "golden"    # Generated by the platform

class IdScope(str, Enum):
    ENTITY = "entity"    # One per unique real-world thing (person, site)
    RECORD = "record"    # One per row (sample, image, genotyping event)

class IdGenMethod(str, Enum):
    UUID = "uuid"            # uuid4(), no config needed
    TEMPLATE = "template"    # Pattern with variables and optional {seq}
    COMPOSITE = "composite"  # Join values from other columns

class ColumnMutability(str, Enum):
    SUBMITTER = "submitter"  # Normal upload column, provided by submitter
    MANAGER = "manager"      # Set/locked by data manager (e.g., site code)
    SYSTEM = "system"        # Generated by platform (golden IDs)

class IdGeneration(BaseModel):
    method: IdGenMethod
    template: str | None = None         # e.g. "GP2-{site}-{seq:05d}"
    components: list[str] | None = None # e.g. ["site", "year", "sample_type"]
    separator: str = "-"                # For composite method
    seq_scope: Literal["group", "global"] = "group"
    # "group" = seq increments per unique combo of other template vars
    # "global" = seq increments across entire gold dataset

class IdentifierDef(BaseModel):
    name: str                           # Column name in gold dataset
    id_class: IdClass                   # source or golden
    scope: IdScope                      # entity or record
    source_columns: list[str] = []      # Which upload columns map to this ID
    generation: IdGeneration | None = None  # How to generate (golden IDs only)
    parent: str | None = None           # Name of parent IdentifierDef (for hierarchy)
    mutability: ColumnMutability = ColumnMutability.SUBMITTER
```

#### DedupStrategy

Controls how incoming records are matched against existing data.

```python
class DedupAction(str, Enum):
    REJECT = "reject"    # Block the submission
    UPDATE = "update"    # Overwrite existing records
    FLAG = "flag"        # Accept but flag for review

class DedupStrategy(BaseModel):
    match_keys: list[str]     # Identifier names to match on
    on_duplicate: DedupAction = DedupAction.REJECT
```

When `match_keys` contains multiple identifiers, a match on **any** key triggers the duplicate action (OR logic). This handles the HRIS case where a person might be found via `old_system_id`, `ssn`, or `dl_number`.

#### AssignmentTiming

When golden IDs are generated in the submission lifecycle.

```python
class AssignmentTiming(str, Enum):
    ON_UPLOAD = "on_upload"    # Auto-assign during validation
    ON_REVIEW = "on_review"    # Reviewer assigns/confirms
    ON_ACCEPT = "on_accept"    # Auto-assign at accept time
```

#### IdentifierScheme

Top-level configuration, stored on the `GoldDataset`.

```python
class IdentifierScheme(BaseModel):
    identifiers: list[IdentifierDef]
    dedup: DedupStrategy
    assignment: AssignmentTiming = AssignmentTiming.ON_ACCEPT
```

### Changes to GoldDataset

```python
class GoldDataset(BaseModel):
    id: UUID
    name: str
    schema_id: str
    schema_name: str
    description: str
    identifier_scheme: IdentifierScheme | None = None  # NEW — replaces key_column
    # key_column: str | None  ← REMOVED
    created_by: str
    record_count: int
    submission_count: int
    created_at: datetime
    updated_at: datetime
```

Backward compatibility: if `identifier_scheme` is `None`, the gold dataset behaves as it does today (no dedup, no ID generation). Existing gold datasets with `key_column` can be migrated by converting to an `IdentifierScheme` with a single source identifier and `dedup.match_keys = [key_column]`.

---

### Column Mutability in the Schema

Golden ID columns and manager-locked columns (like `site`) need special treatment during validation:

- **submitter** columns — normal, expected in uploaded files, validated as usual
- **manager** columns — may be in the upload file or set by the manager at the gold dataset level. Validation does not reject a submission for missing manager columns.
- **system** columns — never in the upload file. Validation ignores these. They are added at ID generation time.

This maps to the schema's `FieldConfig` model. The `mutability` attribute on `IdentifierDef` tells the accept flow which columns to generate vs which to expect in the data.

## Use Case Walkthroughs

### GP2

**Identifier Scheme:**

```json
{
  "identifiers": [
    {
      "name": "site_sample_id",
      "id_class": "source",
      "scope": "entity",
      "source_columns": ["sample_id"],
      "mutability": "submitter"
    },
    {
      "name": "site",
      "id_class": "source",
      "scope": "entity",
      "source_columns": ["site"],
      "mutability": "manager"
    },
    {
      "name": "gp2id",
      "id_class": "golden",
      "scope": "entity",
      "generation": {
        "method": "template",
        "template": "GP2-{site}-{seq:05d}",
        "seq_scope": "group"
      },
      "mutability": "system"
    },
    {
      "name": "gp2sampleid",
      "id_class": "golden",
      "scope": "record",
      "parent": "gp2id",
      "generation": {
        "method": "template",
        "template": "{gp2id}_s{seq}",
        "seq_scope": "group"
      },
      "mutability": "system"
    }
  ],
  "dedup": {
    "match_keys": ["site_sample_id"],
    "on_duplicate": "reject"
  },
  "assignment": "on_accept"
}
```

**Flow:**

1. Site uploads CSV with columns: `sample_id`, `site`, `sex`, `age`, `diagnosis`, ...
2. Validation runs against the schema (field types, required, enums, rules). No golden ID columns expected.
3. Reviewer claims and accepts.
4. Accept flow:
   - Maps `sample_id` → `site_sample_id` (via `source_columns`)
   - Checks `site_sample_id` values against existing gold dataset → rejects if duplicates
   - For new entities: resolves `{site}` from the row's `site` column, finds max seq for that site group, generates `gp2id`
   - For each record: generates `gp2sampleid` using `{gp2id}_s{seq}` (seq per gp2id group)
   - Appends row with all columns: source data + golden IDs + provenance

**Gold dataset row:**

```
site_sample_id | site  | gp2id           | gp2sampleid        | sex | age | ... | _submission_id | ...
NRC-0047       | SITE1 | GP2-SITE1-00001 | GP2-SITE1-00001_s1 | M   | 65  | ... | <uuid>         | ...
```

## Implementation

### Sequence Resolution

For `template` generation with `{seq}`, the system needs to determine the next sequence number.

**Group-scoped sequences (`seq_scope: "group"`):**

1. Parse the template to extract non-`{seq}` variables (e.g., `{site}` in `"GP2-{site}-{seq:05d}"`)
2. Resolve those variables from the current row's data
3. Scan existing golden IDs in the gold dataset that match the same group (e.g., all IDs starting with `GP2-SITE1-`)
4. Extract the max sequence number from those IDs
5. Assign next = max + 1

**Global-scoped sequences (`seq_scope: "global"`):**

1. Scan all existing golden IDs in the gold dataset for this column
2. Extract the max sequence number
3. Assign next = max + 1

**CSV backend:** Scan the gold dataset CSV column, parse existing IDs with a regex derived from the template, extract max seq. This is O(n) per accept but acceptable for CSV-scale data.

**Future Postgres backend:** Use a `sequences` table with `(dataset_id, identifier_name, group_key) → current_value`. Atomic increment via `UPDATE ... RETURNING`.

### Parent-Child Resolution

When a child identifier references a `parent`:

1. The parent's golden ID must be resolved first (topological sort on the `parent` graph)
2. The child's template can reference `{parent_name}` — resolved to the parent's generated value for this row
3. The child's `{seq}` is scoped within its parent's value (e.g., `GP2-SITE1-00001_s1`, `GP2-SITE1-00001_s2`)

**Entity vs Record scope interaction:**

If the parent is `entity`-scoped and the child is `record`-scoped, multiple rows with the same entity get the same parent ID but different child IDs. The accept flow must:

1. Group rows by dedup match keys
2. Assign one parent golden ID per unique entity
3. Assign sequential child IDs within each entity

### Dedup Flow (Updated)

The current `find_duplicates(dataset_id, key_column, values)` becomes:

```python
def find_duplicates(
    dataset_id: UUID,
    match_keys: list[MatchKey],  # [{identifier_name, source_column, values}]
) -> DedupResult:
    """
    Check each match key against existing data.
    Returns which keys matched, which values, and the matching rows.
    """
```

Where `DedupResult` contains:
- `has_duplicates: bool`
- `matches: list[DedupMatch]` — each with `identifier_name`, `matched_values`, `existing_row_indices`

The accept flow then applies the configured `on_duplicate` action:
- **reject:** Raise `GoldDuplicateKeyError` with details
- **update:** Overwrite matched rows (preserve golden IDs, update data columns)
- **flag:** Append but add a `_duplicate_flag` provenance column

## API Changes

### Create Gold Dataset

`POST /api/v1/gold/`

```json
{
  "name": "gp2-clinical-pilot",
  "schema_id": "uuid",
  "schema_name": "gp2-clinical",
  "description": "GP2 clinical pilot cohort",
  "identifier_scheme": {
    "identifiers": [ ... ],
    "dedup": { "match_keys": ["site_sample_id"], "on_duplicate": "reject" },
    "assignment": "on_accept"
  }
}
```

`identifier_scheme` is optional. If omitted, the gold dataset has no dedup and no ID generation (same as today without `key_column`).

### Get Gold Dataset

`GET /api/v1/gold/{id}`

Response includes `identifier_scheme` in full.

### Accept Submission (Updated Response)

`POST /api/v1/submissions/{id}/accept`

On success, the response now includes:

```json
{
  "rows_appended": 50,
  "ids_generated": {
    "gp2id": { "new": 45, "existing": 5 },
    "gp2sampleid": { "new": 50 }
  }
}
```

## Migration

Existing gold datasets with `key_column` set should be migrated:

```python
# Migration: key_column → identifier_scheme
if dataset.key_column:
    dataset.identifier_scheme = IdentifierScheme(
        identifiers=[
            IdentifierDef(
                name=dataset.key_column,
                id_class=IdClass.SOURCE,
                scope=IdScope.RECORD,
                source_columns=[dataset.key_column],
                mutability=ColumnMutability.SUBMITTER,
            )
        ],
        dedup=DedupStrategy(
            match_keys=[dataset.key_column],
            on_duplicate=DedupAction.REJECT,
        ),
    )
```

This preserves current behavior exactly.

## Verification

1. **Unit tests:**
   - `IdentifierScheme` model validation (valid configs, invalid parent references, etc.)
   - Sequence resolution: group-scoped and global-scoped
   - Parent-child ordering (topological sort)
   - Dedup with single and multiple match keys
   - ID generation for all three methods (uuid, template, composite)
   - Migration from `key_column` to `identifier_scheme`

   - Create gold dataset with GP2-style identifier scheme
   - Upload and accept submission → verify golden IDs generated correctly
   - Upload second submission with duplicate source IDs → verify rejection
   - Upload second submission with new source IDs → verify sequence continues
   - HRIS-style: verify dedup across multiple source ID columns (OR logic)
   - UUID method: verify unique IDs generated without naming convention

3. **Manual test:**
   - Create gold dataset via API with identifier scheme
   - Upload CSV, accept, download gold dataset CSV
   - Verify golden ID columns present with correct values
   - Upload second CSV with overlap → verify dedup behavior
