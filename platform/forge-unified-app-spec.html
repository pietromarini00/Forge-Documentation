Forge Unified App — MVP Specification

Status: Phase 4 Complete Last updated: 2026-02-28 (Phase 4 complete) Depends on: Executive Summary · Production Roadmap

1. Overview

Problem

Forge currently ships as four separate services on four different ports. An internal user testing the full data lifecycle must:

  1. Open the Curation Workbench (:8502) to create a canonical schema

  2. Query the Registry API (:8000) to verify the schema was published

  3. Open the Harmonization Engine (:8501) to map incoming data to the schema

  4. Open the DataForge UI (:8503) to validate, review, and accept the data

This means three browser tabs, three separate session states, no shared navigation, and zero contextual handoff between steps. Users must mentally track which schema they’re working with and manually re-select it in each tool.

Solution

Ship a single Streamlit multi-page application (“Forge”) that unifies all three user-facing services into one coherent workflow. The backend APIs (Registry Service, DataForge API) remain unchanged. The unified app is a new UI layer that consumes these APIs and consolidates the existing Streamlit UIs.

Goals

  • Single entry point — One URL, one sidebar, one identity for internal testers

  • Schema-centric workflow — Select a schema once; it flows into harmonization and validation

  • Contextual handoffs — Finish one step, launch the next with context pre-loaded

  • Preserve what works — Existing wizard flows are proven; extract and re-use, don’t rewrite

  • Test the full loop — Internal users can exercise Create → Map → Validate → Review end-to-end

Non-Goals (MVP)

  • User authentication (Supabase Auth is a later phase)

  • Roles, organizations, or permissions (post-MVP)

  • React frontend migration (post-MVP, after workflows are validated)

  • Value transforms in harmonization (Phase B feature)

  • Cross-submission validation in DataForge

  • Schema evolution / variable addition requests

  • Public/external user access

3. Data Model: Two Project Types

Design Rationale

Schemas and data have fundamentally different lifecycles:

  • One schema → many data projects. A canonical schema (e.g., “NINDS CDEs v2”) is created once by a schema manager. Dozens of data managers then use that schema to map and validate their datasets.

  • Schema curation is creative work. It involves AI-assisted deduplication, naming standardization, constraint definition. It’s a standalone workflow.

  • Data mapping + validation is operational work. It involves uploading files, running matchers, reviewing results. It naturally flows as one continuous process.

Therefore:

Project Type

Scope

Lifecycle

Schema Project

Creating/evolving a canonical schema

Upload CDE list → Curate → Publish to Registry

Data Project

Mapping + validating data against a schema

Select schema → (optional) Harmonize → Upload to DataForge → Review

Schema Project Manifest

class SchemaProjectManifest:
    """Tracks a schema curation effort."""
    project_id: str                  # UUID
    project_name: str                # Display name
    user_id: str                     # Creator identity
    current_step: int                # 1–4
    created_at: datetime
    modified_at: datetime

    # Curation state
    source_filename: str             # Original CDE list file
    source_row_count: int
    variable_count: int              # After initial parse
    completed_variables: int         # Curation progress

    # Outcome
    published_schema_id: str | None  # Registry UUID after publish
    published_schema_name: str | None

    steps: dict[str, StepMetadata]   # 1_upload, 2_configure, 3_curate, 4_publish

Data Project Manifest

class DataProjectManifest:
    """Tracks a data mapping + validation effort."""
    project_id: str                  # UUID
    project_name: str                # Display name
    user_id: str                     # Creator identity
    created_at: datetime
    modified_at: datetime

    # Schema reference (set once during project creation)
    schema_id: str                   # Registry UUID
    schema_name: str                 # Display name (cached for UI)
    schema_version: int              # Version at time of selection

    # Harmonization state (optional — user may skip)
    harmonization_enabled: bool      # Whether user chose to harmonize
    harmonization_step: int | None   # 1–3 (setup, match, curate)
    harmonization_complete: bool
    mapping_artifact_path: str | None  # Path to exported mapping JSON

    # DataForge state
    submission_ids: list[str]        # DataForge submission UUIDs
    active_submission_id: str | None # Current submission being worked on

    steps: dict[str, StepMetadata]   # Dynamic based on harmonization_enabled

Schema Selector Component

A shared dropdown that queries the Registry Service and returns the selected schema. Used by Data Project creation and anywhere a schema reference is needed.

def schema_selector(
    registry_client: RegistryClient,
    label: str = "Select a canonical schema",

    filter_published: bool = True,

    """
    Renders a selectbox of available schemas from the Registry.
    Returns SchemaInfo(id, name, display_name, version, element_count) or None.
    """

Display format: "{display_name} (v{version}, {element_count} elements)"

Description

6. User Journeys

Journey A: Create a Schema and Use It (Full Loop)

1. User opens Forge → Home
2. Clicks "+ Create Schema" → Schemas page, curation wizard
3. Step 1: Uploads CDE list (CSV with 520 variables)
4. Step 2: Configures naming (snake_case), sets similarity threshold (0.80)
5. Step 3: Curates variables one by one
   - AI suggests canonical names, types, constraints
   - Duplicate detection flags 47 pairs → user merges/keeps
   - Progress: 520 → 450 canonical elements
6. Step 4: Sets schema name "NINDS CDEs", description → Publishes to Registry
7. Sees success → Clicks "Use this schema → Create a Data Project"
8. → Navigates to Harmonize page, new Data Project dialog
9. Names project "GP2 Study A", schema pre-selected as "NINDS CDEs v2"
10. Step 1: Uploads data dictionary (156 columns)
11. Step 2: AI matches fields → 130 high-confidence, 20 medium, 6 low
12. Step 3: Curates uncertain matches → 142 mapped, 14 intentionally unmapped
13. Clicks "Proceed to validation →"
14. → Navigates to Data page, upload wizard with project context
15. Step 1: Project and schema pre-filled
16. Step 2: Uploads actual data CSV (347 rows)
17. Step 3: Validation report shows 12 errors, 5 warnings
18. Downloads report, fixes source data, re-uploads
19. Step 3: Clean validation → Submits for review
20. Another user claims and reviews → Accepts
21. Data is in the system ✅

Journey B: Validate Data Against an Existing Schema (Skip Harmonization)

1. User opens Forge → Home
2. Clicks "+ Upload Data (Quick)"
3. → Data page, upload wizard
4. Step 1: Selects "NINDS CDEs v2" from schema dropdown, enters study name
5. Step 2: Uploads CSV (columns already match canonical schema names)
6. Step 3: Validation report → clean → Submits for review

This journey skips harmonization entirely. The user’s data already conforms to the schema.

Journey C: Map Data to an Existing Schema (No Curation Needed)

1. User opens Forge → Harmonize

10. Decisions (Resolved)

  1. Mapping application during upload: Auto-apply column renames from the harmonization mapping with a preview confirmation step. The original source-to-canonical mapping is always retained and viewable — users can inspect the mapping for any variable at any time. The mapping artifact is a first-class object in the Data Project, never discarded.

  2. Schema version pinning: Yes. Data Projects pin to the schema version at creation time. Validation results are meaningless if the schema shifts underneath them. Users can create a new Data Project to use a newer schema version, or an explicit “upgrade schema version” action can be added post-MVP.

  3. Project storage: Local filesystem cache (.cache/forge-app/) for MVP. Migrate to Supabase after the MVP is built and validated with internal users, aligned with the C.1-Infra persistence migration track.

  4. Standalone service deprecation: Keep deployable, mark as legacy. The standalone Streamlit apps (:8501, :8502, :8503) remain in the repo as fallbacks and for isolated service testing. READMEs updated to point to the unified app as the primary interface. No further UI investment in standalone apps once the unified app covers equivalent functionality.

  5. Schema validation rules in Registry: Keep as DataForge-specific config tied to schema_id for now. Validation rules are operational concerns (data quality), not schema definition. If multiple Data Projects duplicate the same rules for the same schema, that’s the signal to promote rules into Registry.
